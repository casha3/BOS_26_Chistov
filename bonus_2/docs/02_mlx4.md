# 2. Драйвер mlx4: назначение, версии ядра, точка фокуса

## Что это

`drivers/net/ethernet/mellanox/mlx4/` — семейство драйверов Mellanox
ConnectX-3 / ConnectX-3 Pro (MT27500/MT27520):

| Модуль | Назначение |
|---|---|
| `mlx4_core` | PCI-драйвер: firmware-команды (HCR), контекстная память (ICM), EQs/CQs/QPs, SR-IOV |
| `mlx4_en` | Ethernet-функция: netdev, ethtool_ops, ndo_open/stop, RX/TX rings, steering |
| `mlx4_ib` | InfiniBand/RDMA (в проекте выключен: `CONFIG_MLX4_INFINIBAND=n`) |

PCI ID: `15b3:1003` (ConnectX-3), `15b3:1007` (ConnectX-3 Pro). Драйвер
поддерживает и VF (`1004`), но для PF-эмуляции достаточно `1003`.

## Версии ядра

Драйвер присутствует во всех актуальных ветках. Мы сознательно берём
**самую свежую стабильную версию** (на момент выполнения — 7.3.6, см.
`tools/versions.env`), потому что:

* ТЗ требует «выбрать самую свежую версию»;
* syzkaller лучше работает с новыми KCOV/KASAN;
* mlx4 не удалён и не помечен deprecated в 7.x (проверено по исходникам
  `v7.3.6`: `mlx4_core`, `mlx4_en`, `mlx4_ib` на месте).

Дополнительно модель устройства проверена на ядре **6.18.60** (Alpine virt):
это ближайшая LTS, поведение firmware-интерфейса идентично.

## Что именно фаззим

Административная поверхность, доступная из userspace:

| Интерфейс | Код драйвера |
|---|---|
| `ioctl(SIOCETHTOOL)` | `mlx4_en_ethtool_ops` (`get_drvinfo`, `get_link_ksettings`, `get/set_coalesce`, `get/set_ringparam`, `get_channels`, `get/set_pauseparam`, `get_strings`, `get_sset_count`, `get_ethtool_stats`, `get_module_info/eeprom`, `set_features`, `get/set_rxfh`) |
| `ioctl(SIOCSIFMTU)` | `mlx4_en_change_mtu` |
| `ioctl(SIOCSIFHWADDR)` | `mlx4_en_set_mac` |
| `ioctl(SIOCSIFFLAGS)` | `mlx4_en_open`/`mlx4_en_close` → `mlx4_en_start_port/stop_port` |
| `ioctl(SIOCADDMULTI/DELMULTI)` | `mlx4_en_set_rx_mode` |
| netlink devlink | `mlx4_core` devlink-порты (тип порта, split) |
| sysfs | атрибуты PCI-устройства и netdev |

Именно эти пути попадают в `focus_areas` (`^drivers/net/ethernet/mellanox/mlx4/`).

## Почему это интересная цель

* драйвер общается с устройством через firmware-команды, и **ответы устройства
  не доверенные** (в реальной жизни — скомпрометированная прошивка/малиционный
  hypervisor);
* наша модель умеет отдавать «злые» значения (`evil=on`): некорректный MTU,
  невалидный MAC, странный transceiver, что заставляет драйвер идти в
  граничные ветки;
* mlx4_en почти не покрыт syzkaller-фаззингом на syzbot из-за отсутствия
  железа в облаке — поэтому даже простая эмуляция даёт новое покрытие.

## Ограничения модели

* Нет data path (TX/RX descriptors игнорируются) — фаззинг административный,
  не пакетный;
* нет SR-IOV/VF, нет `mlx4_ib`;
* проверены команды, которые драйвер реально шлёт при probe и в ethtool-путях;
  неизвестные команды завершаются успешно и логируются (`verbose=on`).
